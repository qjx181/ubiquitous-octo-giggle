## Q1 🔴 项目是做什么的？解决了什么问题？

**面试官：** 请简单介绍一下你这个项目。

**我的回答（原版）：**
> 企业内部招股说明书问答系统，给招股说明书当做RAG的外挂知识库，通过检索知识库的内容回答问题，能够节省时间。

**问题：** 只说"做什么"没说"亮点"，"节省时间"太笼统。

**改进版（背这个）：**
> "这是一个基于 RAG 架构的招股说明书智能问答系统。核心价值是：用户提问后，系统自动到知识库中检索最相关的文档片段，再交给大语言模型生成基于事实的回答。相比人工翻阅几百页 PDF，能把查找时间从小时级降到秒级。
>
> 关键设计上做了三个事：
> ① **智能分流**——简单问题走小模型（快响应省资源），复杂问题走大模型（保质量）
> ② **自动探测**——系统自己判断哪些功能可用，不用手动配置
> ③ **多级降级**——某个环节出错了不会崩，自动用备选方案兜底"

---

## Q2 🔴 整个请求从发出到拿到答案，完整流程是什么？

**面试官：** 用户点击发送到页面显示答案，中间经历了什么？

**我的回答（原版）：**
> 用户提出问题 → BGE-M3转向量 → Milvus语义检索 → BM25关键字检索 → 混合检索 → RRF汇总 → Reranker重排 → LLM生成答案 → 流式返回前端。

**问题：** 漏了 Query理解、缓存检查、降级策略三个关键环节。面试官会追问"BM25坏了怎么办？"——你没提前说降级方案。

**改进版（背这个）：**
> "用户提问后分7步：
>
> ① **查缓存**——先查 Redis，同样问题直接返回，不走管道
> ② **Query理解**——判断是问候语还是专业问题，问候直接返回，专业问题规范化查询
> ③ **Embedding编码**——BGE-M3 转1024维向量
> ④ **多路检索**——同时走 Milvus 向量检索 和 BM25 关键字检索（BM25不可用则降级为纯向量检索）
> ⑤ **RRF融合排序**——不看分数只看排名，解决向量分和BM25分不可比的问题
> ⑥ **Reranker精排**——Cross-Encoder 重排序（模型加载失败则降级跳过）
> ⑦ **LLM生成**——根据问题复杂度选择 SGLang(复杂) 或 Ollama(简单) 生成答案，流式接口先发 sources 再逐 token 推答案"

## Q3 🔴 流式接口和普通接口为什么分开？

**面试官：** 为什么分两个接口？合并成一个不行吗？

**我的回答（原版）：**
> 因为流式回答是逐步回答的，而答案来源是早已准备好的，做不了流式输出。普通回答等答案完全生成后和来源一起发送。

**问题：** "做不了流式输出"不对——现在项目里已经能先发 sources 再流式推答案了。核心矛盾是返回格式不兼容。

**改进版（背这个）：**
> "因为两个接口返回的格式完全不同。普通接口返回完整 JSON——包含 answer 和 sources。流式接口返回 SSE 文本流，每次推送一个 token。这两个格式无法合并——放在同一个接口里，前端既要解析 JSON 又要处理 SSE 文本流，解析复杂度翻倍。
>
> 至于 sources，它在检索阶段就已经确定了，理论上也可以在流式输出前发 sources。我现在就是这么做的——流式接口先发一段 JSON 包含 sources，再逐 token 推 answer。即便如此，两个接口还是分开——因为一个要等全部生成完才返回，一个要边生成边返回，内部实现逻辑完全不同。"

## Q4 ⚡ 流式接口里 sources 怎么在流里捎带？

**面试官（追问）：** 你说 sources 在检索阶段就确定了，技术上怎么在流式响应里捎带？

**回答：**
> "我现在的实现是：第一步先执行检索管道拿到 sources，不作为 SSE 文本直接推送，而是包装成 JSON 事件发给前端——格式是 `data: {"type":"sources","data":[...]}\n\n`。前端收到后判断 data 是否能解析为 JSON 且包含 type 字段，有则渲染引用来源，没有则追加到答案文本框。这样来源和答案在同一个流里都有了。"

## Q5 🔴 CORS 为什么放最外层？放错顺序会怎样？

**面试官：** 三个中间件（CORS、Logging、RateLimit），为什么 CORS 在最外层？

**我的回答（原版）：**
> 因为 FastAPI 是后添加先执行结构，把 CORS 放在最外面是要先执行他，让用户跨域头访问。如果先执行 RateLimit 触发了 429 报错，我们就发现不了是 CORS 的错误。

**问题：** 重点偏了。429 没错，问题是浏览器因为缺跨域头报 CORS 错误，**掩盖了真正的 429 状态码**。你以为跨域没配好，其实是限流了。

**改进版（背这个）：**
> "FastAPI 中间件是后添加先执行的栈结构。代码添加顺序是 RateLimit → Logging → CORS，但实际请求进来时，先经过 CORS（最后添加的），再经过 Logging，最后经过 RateLimit。CORS 在最外层确保所有响应都有跨域头——包括被 RateLimit 拒绝的 429 请求。如果 CORS 在内层，RateLimit 拒绝后直接返回，没经过 CORS，浏览器会因为缺少跨域头报 CORS 错误而不是显示 429——你以为是跨域没配对，实际上是限流了，调试起来很绕。"

**追问：** allow_origins=["*"] 有什么安全风险？
> "允许所有来源，任意网站都可以发请求。生产环境要改成具体域名白名单。注意 allow_credentials=True 时 origin 不能是 *，必须显式指定。"

---

## Q6 ⚡ CORS 和 Logging 顺序反了会怎样？

**面试官：** 如果 Logging 在最外层，CORS 在中间，会出什么问题？

**回答：**
> "Logging 在外侧会让每次被 CORS 拒绝的预检请求（OPTIONS）都写入日志。但这些被拒绝的请求是正常行为，不是错误——日志里就多了一堆无意义的 OPTIONS 记录。所以 CORS 在最外层是最佳顺序：被 CORS 拒绝的请求根本到不了 Logging，日志里只记录真实进到业务逻辑的请求，干净好查。"
