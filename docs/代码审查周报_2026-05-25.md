## 一、总体评价

### 优点 ✅

1. **架构清晰**：离线管道（PDF解析→分块→向量化→导入Milvus）与在线服务（FastAPI→检索→LLM生成）完全分离，职责明确。

## 二、P0 — 必须修复（安全/正确性）

### 2.1 `llm_router.py` — IP/端口硬编码（多处）

**位置**：`llm_router.py` 第 46 行、第 95 行

```python
# 第 46 行（_check_service 中）
sglang_check_host = "http://172.23.190.86:30000"
# ...

# 第 95 行（_create_client 中）
client.host = "http://172.23.190.86:30000"
```

**严重性**：P0 — 参数欺骗

**问题**：
1. 硬编码 WSL 内网 IP `172.23.190.86` 分别在 `_check_service` 和 `_create_client` 中出现两次。WSL 重启后 IP 会变化，服务将不可用。
2. `_create_client(provider, host, model)` 函数签名声明了 host 和 model 参数，但在 sglang 分支中完全忽略参数值，直接用硬编码值。签名与实现不一致。
3. `settings.SGLANG_HOST` 配置项（定义为 `http://localhost:30000`）实际未被使用。

**建议修复**：
- 统一使用 `settings.SGLANG_HOST` 作为 SGLang 目标地址
- 删除 `sglang_check_host` 局部变量
- `_create_client` 中 sglang 分支也应使用传入的 host 参数

### 2.2 `llm_router.py` — `model="default"` 占位符

**位置**：第 96 行

```python
client.model = "default"
```

**严重性**：P0 — 语义错误

**问题**：此值会写入 API 请求体的 model 字段。虽然 SGLang 忽略此字段，但若将来换用不忽略 model 字段的服务（如兼容 OpenAI API 的其他推理引擎），`"default"` 会导致 400 错误。同时使代码阅读者困惑。

**建议修复**：
- 改用 `settings.SGLANG_MODEL` 的真实值
- 或在注释中明确说明"此字段被 SGLang 忽略，填任意非空值"

### 2.3 `llm_router.py` — `__init__` 中同步 HTTP 调用

**位置**：第 46-48 行

```python
self.sglang_available = self._check_service(sglang_check_host, "SGLang")
self.ollama_available = self._check_service(settings.OLLAMA_HOST, "Ollama")
```

**严重性**：P0 — 阻塞启动

**问题**：`__init__` 是同步方法，`_check_service` 使用 `httpx.get(timeout=2)` 会阻塞事件循环。如果 LLM 服务未启动，每个超时等待 2 秒，加起来最多 4 秒。更重要的是，如果 LLMRouter 在 `get_llm_router()` 首次调用时初始化失败（两个服务都超时），会 raise `RuntimeError("没有可用的LLM服务")`，导致整个服务启动失败。

**建议修复**：
- 将 LLM 服务检测改为异步（放在 `startup` 事件中）
- 或将其改为懒检测——首次调用 `generate()` 时再检测

## 三、P1 — 建议修复（代码质量/架构）

### 3.1 `llm_client.py` — 单 Provider 绑定

**位置**：第 29-53 行 (`__init__`)

**问题**：`LLMClient` 通过 `settings.LLM_PROVIDER` 绑定单个云端 Provider。而 `LLMRouter` 在 SGLang 和 Ollama 之间做智能路由。云端 API（SiliconFlow/DeepSeek）不在路由体系内，无法实现"简单问题→便宜模型，复杂问题→贵模型"的分级路由。

**影响**：若同时配置多个云端 API，只能选一个。扩展性受限。

**建议修复**：参考 LLMRouter 的多引擎模式，将云端 API 也纳入 `LLMRouter` 的智能路由体系。

### 3.2 `rate_limit.py` — 内存限流非分布式

**位置**：`rate_limit.py` 第 67 行

```python
self.requests: Dict[str, list] = {}
```

**问题**：限流状态保存在进程内存中。`config.py` 设了 `WORKERS=4`，多 worker 时每个进程独立计数，实际限流效果打折扣（4×100次/分=400次/分）。此外服务重启后限流记录丢失。

**建议修复**：生产环境改用 Redis 实现分布式滑动窗口限流。

### 3.3 `milvus_client.py` — Milvus 连接无健康检查/重连

**位置**：`milvus_client.py` 第 57-89 行

**问题**：`_connect()` 仅在 `__init__` 中调用一次。如果 Milvus 在运行时断开（如网络抖动、服务重启），后续所有 `search()` 都会失败。没有重连机制。

**建议修复**：
- 给 MilvusClient 添加连接健康检查（定期 ping）
- 或捕获连接错误后自动重连

### 3.4 `retrieval.py` — HybridRetriever 从未真正创建

**位置**：`_probe_hybrid_retrieval()` 第 162 行

```python
self.hybrid_retriever = None  # 通过探测后仍设为 None
```

但在 `_run_retrieval_pipeline` 第 367 行：
```python
if self.features["hybrid_retrieval"] and self.hybrid_retriever:
```

由于 `hybrid_retriever` 始终为 `None`，混合检索功能实际上**从未真正启用**。probe 通过了，但 feature 永远不会被执行。

**建议修复**：
- 在 _probe_hybrid_retrieval 中检测通过后，真正创建 HybridRetriever 实例
- 或在首次使用前执行懒加载

### 3.5 `retrieval.py` — 子查询被丢弃

**位置**：`_run_retrieval_pipeline` 第 353-355 行

```python
if u.sub_queries and len(u.sub_queries) > 1:
    q = u.sub_queries[0]  # 只取了第一个子查询
```

**问题**：QueryUnderstandingService 的问题分解功能（`_decompose_query`）可以生成多个子查询（如对比类问题拆成两家公司分别检索），但实际只用了第一个，其余被丢弃。多路检索功能未实现。

**建议修复**：多子查询应分别检索后合并（RRF 融合），而非丢弃。

## 四、P2 — 优化建议（性能/可维护性）

### 4.1 `redis_client.py` — print 语句代替 logger

**位置**：`redis_client.py` 第 111、149、183、203、238 行

```python
print(f"Warning: Redis connection failed: {e}")
```

**问题**：在线服务代码中使用了 `print()` 而不是 `logger`。虽然在 Python 3 中 print 默认输出到 stdout 也不报错，但无法进行日志级别过滤、日志轮转、集中收集（如 ELK）。

**建议修复**：将 `print` 全部替换为 `logger.warning()`。

### 4.2 `llm_client.py` — 流式接口返回类型兼容性

**位置**：`llm_client.py` — `generate_stream()`

**问题**：LLMRouter 的 `generate_stream` 与 LLMClient 的 `generate_stream` 路径存在类型兼容问题。LLMClient 返回 `AsyncGenerator`，部分 Ollama 路径下可能返回 `HTTPStream`。

**建议修复**：统一 Stream 适配器，确保外部生成器使用统一的 `async for` 接口。

### 4.3 `rb25_retriever.py` — BM25 索引内存消耗

**问题**：`BM25Retriever.build_index()` 将全量文档驻留在内存中（`self.documents` 和 `self.tokenized_docs`）。对于万级文档尚可，超过 HYBRID_MAX_DOCS=10000 时内存可能快速增长。

**建议修复**：考虑用 `whoosh` 或 `elasticsearch` 替代内存 BM25。

### 4.4 配置文件碎片化

**问题**：存在两套配置文件：
- `config.py`（根目录）— 离线管道使用普通常量
- `backend/app/config.py` — 在线服务使用 pydantic-settings

两者定义了部分重叠的配置项（如 `MILVUS_HOST`、`EMBEDDING_DIM`），但没有同步机制。修改一处而忘记另一处会导致配置漂移。

**建议修复**：
- 统一使用 pydantic-settings（离线管道也通过环境变量或默认值配置）
- 或将共用的配置项提取到共享模块

### 4.5 `check_imports.py` — 导入路径问题

**位置**：`check_imports.py` 第 82-85 行

```python
try:
    from app.db.milvus_client import MilvusClient
```

**问题**：在线服务中 `milvus_client.py` 导出的类名是 `MilvusClientWrapper` 而非 `MilvusClient`（后者是 pymilvus 自带的类）。这个 import 要么失败，要么错误地导入了 pymilvus 自带的 `MilvusClient`，从而导致检查不准确。
