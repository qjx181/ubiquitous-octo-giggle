## 一、服务框架：main.py + chat.py（6题）

### Q1 中间件有三层，为什么CORS在最外层？

**回答：**
FastAPI 中间件是"后添加先执行"的栈结构。代码顺序是 RateLimit → Logging → CORS，但请求进来时先经过 CORS（最后添加的）。CORS 在最外层确保**所有响应**都有跨域头——包括被 RateLimit 拒绝的 429 请求。如果 CORS 在内层，RateLimit 拒绝后直接返回，没经过 CORS，浏览器会因为缺跨域头报 CORS 错误而非显示 429。

**追问1：** 那 CORS 和日志的顺序反过来会怎样？
> Logging 在 CORS 之外的话，被 CORS 拒绝的跨域请求（options 预检）就记不到日志里。所以 Logging 应该在 CORS 和 RateLimit 之间——既能记录预检请求，又能记录被限流的请求。

**追问2：** allow_origins=["*"] 有什么安全风险？生产环境怎么改？
> 允许所有来源意味着任意网站都可以发请求。生产环境应改为具体的域名白名单，比如 `["https://myapp.com"]`。注意 allow_credentials=True 时 origin 不能是 "*"，必须显式指定。
> 
     > "开发时用  方便调试。上线前必须改成具体的域名白名单。如果前端要传 Cookie，allow_credentials=True 就不能用
     ，必须显式列域名——这是浏览器的安全规范。不过说实话，CORS 只防浏览器端的跨域攻击，真正的接口防护要靠 JWT 认证 + HTTPS + 限流。"

### Q2 启动事件为什么不加载模型？

**回答：**
启动事件只打印日志，不做任何重量级初始化。因为如果模型加载（BGE-M3 的 2GB 文件）放在 startup 事件里，文件损坏或磁盘异常会导致整个服务崩溃。懒加载把风险推迟到首次请求——那次请求可能失败服务降级，但服务本身还在跑，/health 还能返回正常。

**追问1：** 首次请求慢怎么优化？
> 可以用一个预热端点，部署后在健康检查脚本里先发一个请求触发模型加载，这样用户首次请求就不等了。或者把模型加载放在 FastAPI 的 lifespan 里做异步预加载。

**追问2：** 如果模型加载一直失败怎么办？
> 返回降级结果，比如提示"知识库暂时不可用"。同时日志记录详细错误，配合告警通知运维。关键原则：不因为非核心依赖崩溃。

---

### Q3 为什么单进程 workers=1？

**回答：**
workers>1 会启动多进程，每个进程独立加载一次模型（BGE-M3 + Reranker ≈ 3GB），8GB 显存撑不住。单进程 + FastAPI 异步非阻塞足以处理高并发——模型推理是 GPU 操作，本身就是串行的，多进程反而因为 GPU 争抢降低吞吐。

**追问1：** 单进程如果被阻塞了怎么办？
> FastAPI 是异步框架，I/O 操作（Redis 查询、Milvus 搜索、LLM HTTP 调用）用 async/await 不会阻塞。CPU 计算（Embedding 编码）用线程池隔离。真正会阻塞的是同步代码里的 time.sleep，我们通过代码审查确保没有这类问题。

**追问2：** 那怎么扩展？一台机器不够用？
> 横向扩展——多台机器，每台单进程，前面挂负载均衡器。也可以用 Docker Swarm / K8s 自动扩缩容。

### Q4 普通问答和流式问答为什么分两个接口？

**回答：**
返回格式完全不同。普通接口返回完整 JSON，包含 answer 和 sources 两个字段。流式接口返回 SSE 文本流，逐 token 推送。如果合并成一个，前端既要解析 JSON 又要处理文本流，解析复杂度翻倍。而且 sources 在检索阶段就确定了，比 LLM 生成早，不能在流中捎带。

**追问1：** 如果我想既流式又带 sources，怎么改？
> 在流开始前先发一段 JSON 包含 sources，再逐 token 发 answer。前端判断流的前几个字节是 JSON 还是文本来决定解析方式。这会增加前端复杂度，但体验更好。

**追问2：** SSE 的 [DONE] 标记是做什么的？
> 前端无法知道 LLM 什么时候生成完毕（因为没有 Content-Length）。[DONE] 让前端明确知道流已结束，可以关闭 loading 状态。这是 OpenAI SSE 格式的业界惯例。

### Q5 **source 是什么语法？为什么要用它？

**回答：**
`**` 是 Python 的字典解包操作符。`result["sources"]` 是一个字典列表，每个字典包含 text/page/section/score 等字段。`Source(**source)` 把字典展开成关键字参数传给 Source 的构造函数，相当于 `Source(text=..., page=..., ...)`。这样做的目的是把普通 dict 转换成 Pydantic 模型，让 FastAPI 自动做类型校验和序列化。

**追问1：** 如果字典的 key 和模型字段名不一致怎么办？
> 手动映射：`Source(text=source["content"], page=source["pg_num"])`。或者用 Pydantic 的 alias 功能在字段上声明别名。

**追问2：** 为什么不直接用 dict 返回？
> 因为 ChatResponse 的签名声明了 `sources: List[Source]`，Pydantic 会校验每个 Source 对象的字段类型（page 必须是 int 等）。直接传 dict 会丢失类型校验。

---

### Q6 业务异常和系统异常为什么分开处理？

**回答：**
BusinessException 是预期内错误（如检索不到信息），有明确的业务含义，返回 404 让前端展示"未找到相关信息"。系统异常（如数据库连不上）是预期外错误，返回 500 且不暴露内部细节。分开两层，让调用方可以根据异常类型做不同处理——业务异常前端可以给用户看，系统异常只记日志。

**追问1：** 流式接口为什么 yield 错误文本而不抛异常？
> 因为 Generator 抛异常后调用方捕获很麻烦——yield from 的链式调用会让异常传播变得复杂。不如直接 yield 一段 "生成失败：xxx" 文本，前端直接展示，连接不会断。

## 二、自动探测 + 智能降级（3题）

### Q7 自动探测（probe）怎么实现的？为什么不用手动配置？

**回答：**
`__init__` 中调用 4 个 `_probe_xxx` 方法，每个独立 try-except。探测成功 → `features[key]=True`，失败 → features 保持 False。运行时通过 features 字典决定是否调用该功能。手动配置的问题：改了配置要重启，而且可能忘记开。自动探测适配环境动态变化（今天开了 Redis 明天没开），零运维负担。

**追问1：** 如果某个 probe 抛异常了，服务会怎样？
> 不会崩溃。所有 probe 都有 try-except，异常只记录日志，features 保持 False。设计原则：宁可少一个功能，不让服务崩溃。这是容错设计。

**追问2：** features 字典在运行时能动态变化吗？
> 目前是静态的——只在初始化时探测一次。如果要支持运行时动态（比如 Redis 断了又恢复后自动启用），要加心跳机制周期性重试 probe。当前设计倾向于简单，运行时动态是未来改进方向。

---

### Q8 三级降级策略是怎么实现的？

**回答：**
以 Reranker 为例：① 异步预加载——后台 daemon 线程加载模型，不阻塞主线程；② 同步等待 60 秒——如果第一个请求进来时后台还没加载完，`_lazy_load_reranker()` 在主线程等最多 60 秒；③ 彻底降级——等不到或同步加载也失败，features["reranker"]=False，跳过重排直接用检索结果。

**追问1：** 异步加载和同步等待会不会冲突？
> 不会。`_reranker_loaded` 是一个 threading.Event，后台加载完调用 set()，主线程的 wait(timeout=60) 会立即返回。后台加载成功 → self.reranker 有值 → 后续请求直接用。后台加载失败 → set() 后 self.reranker 仍为 None → 主线程再尝试同步加载一次。

**追问2：** 这个模式还能用在别的地方吗？
> 可以。任何启动慢但非核心的功能都可以用这个模式——比如启动时加载一个词云模型、一个情感分析模型。核心服务先起来，可选功能慢慢加载。

---

### Q9 检索结果为空为什么不调 LLM？

**回答：**
这是 RAG 的核心原则："不知道就是不知道"。如果检索不到相关文档，强行让 LLM 基于空上下文生成会导致幻觉（Hallucination）——LLM 会编造看似合理但实为虚构的答案。所以检索结果为空时直接抛 BusinessException("未找到相关信息")，前端展示提示。

**追问1：** 但有些问题不需要检索啊，比如"你好"？
> 所以检索之前有 Query 理解模块做意图分类。问候语、闲聊等不需要检索的请求，在 Query 理解阶段就直接返回了，不进检索管道。只有真正需要知识库回答的问题才走检索。

**追问2：** 如果我非要让 LLM 基于已有知识回答呢？
> 可以加一个 fallback 模式：检索为空时用 LLM 的固有知识回答，但响应里标注 "仅供参考，非知识库内容"。不过金融场景合规要求严格，不建议这么做。

## 三、检索管道：embedding → 检索 → 重排（3题）

### Q10 BGE-M3 的 Embedding 是怎么加载和使用的？

**回答：**
用 SentenceTransformer 库加载本地缓存的 BGE-M3 模型。注意三点：① `local_files_only=True`——不从 HuggingFace 下载，只加载本地缓存（我们通过 ModelScope 下载到本地路径）；② 设置 `device='cuda'`——放到 GPU 上；③ 编码时 `normalize_embeddings=True`——向量归一化，使内积等价于余弦相似度。

**追问1：** 为什么不直接在 HuggingFace 下载？
> 国内网络访问 HuggingFace 不稳定。所以用 ModelScope（阿里镜像）下载后存到本地缓存路径，编码时直接从本地加载。

**追问2：** normalize_embeddings=True 有什么用？
> 归一化后向量模长为1，内积 = 余弦相似度。不归一化时长文本向量的模长更大，内积偏大，检索结果偏向长文本——这不公平。归一化后所有向量在单位球面上，比较的是"方向"而非"长度"。

---

### Q11 Milvus 搜索的参数怎么配置的？

**回答：**
Milvus 搜索配置：`metric_type="IP"`（内积，等价于归一化后的余弦相似度），`params={"nprobe": 128}`（探测聚簇数，控制精度和速度的平衡）。返回 top_k 条结果，每个结果包含 id、embedding、text、page、section、score 等字段。

**追问1：** nprobe=128 怎么确定的？
> nlist=128（建索引时的聚簇数），nprobe 一般等于 nlist。nprobe 越大搜索精度越高但越慢。128 对千条级别的数据量足够。

**追问2：** 为什么用 IP 不用 L2？
> 因为我们已经对向量做了归一化，IP 等价于余弦相似度。在语义搜索场景余弦相似度比 L2 距离更合理——我们关心的是"方向是否一致"而非"距离有多近"。

---

### Q12 Reranker（Cross-Encoder）和普通 Embedding（Bi-Encoder）有什么区别？

**回答：**
Bi-Encoder（BGE-M3）把 Query 和 Doc 分别编码成向量，计算余弦相似度——速度快（全库搜索毫秒级），但 Query 和 Doc 之间缺乏交互，精度有限。Cross-Encoder（BGE-Reranker）把 Query+Doc 拼接在一起送入模型——精度高，但速度慢（只能逐条打分无法预编码）。所以两阶段：Bi-Encoder 粗筛（百→十），Cross-Encoder 精排（十→三）。

**追问1：** 为什么不直接用 Cross-Encoder？
> 因为 Cross-Encoder 不能预编码，必须实时拼接 Query 和每条 Doc。假设有 1000 条文档，就要做 1000 次推理，每次都要处理完整文本。而 Bi-Encoder 可以预编码文档，检索时只需编码一次 Query，再算 1000 次余弦相似度——快几个数量级。

**追问2：** 当前 Reranker 在你的项目里实际启用了没有？
> 本地有模型缓存所以 probe 通过了，但因为异步预加载机制，需要等后台线程加载完成才能使用。当前版本 Reranker 标记为"已就绪"但实际是否生效取决于加载进度。后续改进方向是把异步加载改为初始化时同步预加载（用单独线程，服务启动后等待几秒再接受请求）。

## 四、LLM 路由 / 智能分流（3题）

### Q13 为什么做 LLM 智能分流？

**回答：**
RTX 4060 8GB 显存有限。大模型推理精度高但慢、占显存；轻量模型快但能力弱。智能分流把简单问题（问候、短查询）给 Ollama 上的 0.5B 模型——秒级响应、几乎不占显存；复杂问题（金融分析、多步推理）给 SGLang 上的 1.5B 模型——深度推理、精度高。不分的话：全部走大模型 → 慢、显存压力大；全部走轻量模型 → 复杂问题质量差。

**追问1：** 规则判断准确率多少？误判了怎么办？
> 整体 80-90%。简单问题被误判为复杂的后果＝多花点 Token 和几秒时间，精度更高反而更好。复杂问题被误判为简单的后果＝回答质量可能不够，但不会崩溃——这就是降级策略的价值。改进方向是用小分类模型代替规则。

**追问2：** 两个模型都不可用怎么办？
> 有一个兜底路径：走第三方 API（硅基流动、DeepSeek 等）。配置了 API_HOST、API_MODEL、API_KEY，当本地模型全挂时切换到云端。当然这是最后手段——金融场景数据不出本地是硬要求。

### Q14 LLMClient 为什么用 __new__ 绕过 __init__？

**回答：**
LLMClient 的 `__init__` 设计成从 config 读取一个 provider 来初始化，但 LLMRouter 需要同时持有 SGLang 和 Ollama 两个客户端。用 `object.__new__(LLMClient)` 创建空对象后手动设置 provider/host/model 等属性。这是一个"先跑起来"的 hack——正确做法是把 provider 参数化，让 __init__ 接受参数而非从 config 读取。

**追问1：** 这个 hack 有什么副作用？
> 跳过 __init__ 意味着所有初始化逻辑都不执行——包括超时设置、重试配置等。所以 __new__ 之后要手动设每个属性，漏了一个就报 AttributeError。这也是技术债——需要重构。

**追问2：** 怎么重构？
> 把 LLMClient 的 provider/host/model 改成 `__init__` 参数，`LLMClient(provider="sglang", host="...", model="...")`。LLMRouter 在创建时传不同参数各持一个实例，不再需要 __new__ hack。

### Q15 SGLang 和 Ollama 在部署上有什么区别？

**回答：**
SGLang 需要先跑 `sglang.serve` 加载模型到显存，暴露 OpenAI 兼容的 API 接口。Ollama 更轻量，`ollama run qwen2.5:0.5b` 一行命令启动。SGLang 适合部署需要 batch 推理和连续批处理（continuous batching）的生产环境，吞吐量高。Ollama 适合开发测试、快速原型。

**追问1：** 你的项目里 SGLang 和 Ollama 怎么共存的？
> 两个服务分别监听不同端口（SGLang:30000, Ollama:11434）。LLMRouter 根据复杂度判断结果，选择对应的 client 发送请求。互不可用时自动切换——SGLang挂了走 Ollama 降级，Ollama 挂了或出了问题复杂度达不到阈值走 SGLang。

## 五、性能加速（3题）

### Q16 为什么第一次请求慢，后续就快了？

**回答：**
这是模型懒加载 + 单例模式的效果。BGE-M3 模型首次需要从磁盘加载到 GPU 显存（约 30s，1-2GB 数据），这是硬件决定的物理开销。加载完成后模型常驻 GPU，后续请求只做前向传播（约 300ms）。此外 Milvus 首次连接和 Redis 首次连接也需要少量时间。综合：冷启动 ~35s，热请求 ~3s，约 12 倍加速。

**追问1：** 那 Redis 缓存的作用呢？
> 缓存命中时连检索和 LLM 都不用调——直接从 Redis 返回历史结果。MD5(question|type|top_k) 做键，相同问题秒回。这主要针对用户重复提问的场景。注意需澄清的问题不缓存——因为没有实际结果可以缓存。

**追问2：** 还有没有其他可做的优化？
> ① Reranker 异步预加载已经做了。② HTTP Session 复用——`requests.Session()` 代替 `requests.post()`，省去 TCP 握手。③ 语义缓存——相同语义不同表述的问题也能命中缓存，需要 FAISS 做语义近似匹配。

---

### Q17 单例模式是怎么实现的？

**回答：**
每个服务模块都有一个模块级全局变量 `_service = None` 和一个 `get_service()` 工厂函数。首次调用时创建实例并保存到全局变量，后续直接返回。以 RetrievalService 为例：`get_retrieval_service()` 在第 554-561 行实现——检查全局 `_retrieval_service`，为 None 就创建，否则返回已有的。

**追问1：** 单例和全局变量有什么区别？
> 单例是设计模式——它确保一个类只有一个实例并提供全局访问点。通过工厂函数 `get_service()` 封装，调用方不知道也不关心是不是单例。全局变量是直接暴露的变量，调用方直接访问，无法控制创建逻辑。这里是用全局变量实现单例模式，两者不冲突。

**追问2：** 单例在并发场景下安全吗？
> 对于 RetrievalService 是安全的——它的所有依赖（EmbeddingService、MilvusClient、LLMRouter）本身也是单例，且模型推理是线程安全的。但要注意：如果单例持有可变状态（比如计数器），就需要加锁。当前设计的检索服务是无状态的——每次 query() 调用是独立的，不共享可变数据。

### Q18 Redis 缓存为什么用 MD5 做键？

**回答：**
MD5(question|content_type|top_k) 做缓存键，而不是直接用问题原文。因为问题可能很长（几百字），MD5 固定 32 个字符，省 Redis 内存。注意：MD5 虽然不安全（可碰撞），但做缓存键足够了——碰撞概率极低，即使碰撞了也就是错误地返回了另一个问题的缓存结果，不会造成数据安全问题。

**追问1：** 缓存过期时间为什么是 3600 秒？
> 因为金融数据相对稳定（招股说明书不会每小时更新）。3600 秒（1小时）在响应速度和数据新鲜度之间做了平衡。如果文档频繁更新（比如新闻场景），应该缩短到 300 秒。

**追问2：** 写缓存失败了怎么办？
> 第 296 行 `except: pass`——写失败不影响主流程，只是这次缓存没写进去，下次相同请求会重新检索。这是"写失败不阻塞"的设计原则。

## 六、架构设计综合（4题）

### Q19 你项目里的"企业级"体现在哪些地方？

**回答：**
① **异常分层**——BusinessException 和系统异常分开，不同错误不同处理；② **中间件体系**——CORS、Logging、RateLimit 三层，各自职责清晰；③ **自动探测降级**——4 个增强功能自动检测，不用手动配置，不可用就降级；④ **可配置**——所有参数通过 pydantic-settings 管理，环境变量 / .env 文件 / 代码默认值三级覆盖；⑤ **缓存**——Redis 结果缓存，减少重复计算；⑥ **模型管理**——单例 + 懒加载 + 异步预加载，控制资源消耗。

**追问1：** 日志配置了 JSON 格式，为什么？
> 生产环境通常用 Logstash / Fluentd 收集日志到 ELK 或 Splunk。JSON 格式可以被这些工具自动解析，便于搜索和告警。开发环境则可以用纯文本格式方便阅读。

**追问2：** 限流的 100 次/分钟是怎么确定的？
> 基于实际使用量估算 + 留余量。如果用户人群不超过 10 人，平均每人每分钟 10 次请求，100 次/分钟是合理上限。具体数值应该根据生产环境的实际 QPS 动态调整。

### Q20 离线管道和在线服务的配置为什么分开？

**回答：**
离线管道是批处理脚本，参数相对固定——PDF 路径、chunk 大小、batch size、Milvus 集合名等。用普通常量和常量类就够了，不需要环境变量覆盖。在线服务需要支持 Docker 部署，数据库地址、端口等需要环境变量注入，所以用 pydantic-settings。职责分离：离线配置关注"本地文件路径"，在线配置关注"服务连接参数"。

**追问1：** 会不会出现离线管道导出的向量维度和在线服务不匹配？
> 会。所以离线用 `EMBEDDING_DIM=1024`，在线也一样。如果改了模型（比如换成 768 维的 M3E），两边都要改。一个改进方案是离线管道的维度信息写到 Milvus schema 中，在在线服务初始化时自动读取。

### Q21 config.yaml 和 .env 有什么区别？

**回答：**
.env 存敏感信息——API Key、SECRET_KEY、数据库密码等，不应该提交到 Git。config.yaml 存非敏感配置——模型路径、端口号、检索参数等，可以提交到 Git 作为默认配置。在线服务的 pydantic-settings 同时支持从环境变量和 .env 文件读取，优先级：环境变量 > .env > 代码默认值。
